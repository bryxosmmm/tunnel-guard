# Gerasimov: HMM-MOS, сценарии и начальное направление рельсов

## Решение

Проверена ветка `origin/experiments/gerasimov`, commit `525e276`; исходный наш HEAD — `02083ec`.
Полезную часть интегрировали: процедурные сценарии неподвижного, появляющегося и останавливающегося объекта теперь проходят через **наш настоящий Detector**. Новый CLI `tunnel_guard.motion_scenarios` использует существующий `stress.scene_scan`, сохраняет входной рецепт, исходники, конфигурацию, seed, хеш последовательности облаков и покадровые результаты. Это не новый физически достоверный симулятор.

HMM-MOS не включён в фильтрацию препятствий. Вариант переноса первого измеренного направления рельсов реализован, но оставлен **экспериментальным**: `configs/detector-rail-heading-experimental.json`, поле `rail_initial_heading: fitted`. По умолчанию `zero`, прежнее поведение. Калибровка и пороги не менялись.

## Ревью подхода и кода

Первичные источники: [статья HMM-MOS](https://arxiv.org/html/2410.18638v1), [репозиторий авторов](https://github.com/vb44/HMM-MOS), [прочитанная версия Map.cpp](https://github.com/vb44/HMM-MOS/blob/3f625031d135b2bbe4297125da11facdaba8ca81/src/Map.cpp).

Это сегментация **движущихся** точек через состояния вокселей, а не обнаружение всех физических препятствий. В `Map::update`/переходах состояний (Map.cpp, строки 304–305) переход с участием unobserved исключён из условия начального выделения изменения occupied/free. Из этого не следует, что соседние воксели никогда не дадут ложную метку движения. Остановка объекта и неподвижное препятствие требуют отдельной обработки; использовать MOS как обязательный фильтр кандидатов нельзя. Нашему классонезависимому детектору не требуется ML для сохранения таких объектов.

Замечания к [hmm_mos_probe.py в ветке](https://github.com/bryxosmmm/tunnel-guard/blob/525e276/tunnel_guard/hmm_mos_probe.py):

- `synth`, строки 136–155: комментарий о повторении одного noise/dropout draw не соответствует коду. Один RNG продолжает своё состояние при каждом `scene_scan`; это не одинаковый шум в каждом кадре. Поэтому различие двух режимов не доказывает эффект именно «фиксированный против независимого шума». Наш runner задаёт независимый поток для каждого кадра и проверяемый одинаковый вход между версиями детектора.
- `real`, строки 218–249: позы и облака соединяются по индексу кадра, без проверки timestamp/source/config/deskew. Совпадение количества точек не гарантирует правильную систему координат. Этот адаптер не переносили.
- `synth`, строки 127–144: значение frames внутри case обходит общий limit; object_at получает исходный scene, хотя ray caster получает case_scene. Наш runner использует один явный размер серии и одинаковый case_scene для объекта и лучей.
- `run_hmm_mos`: `/usr/bin/time -l` специфичен для macOS; наличие файла time само по себе не делает этот аргумент переносимым на Linux.

Бинарник HMM-MOS **не собирался и не запускался нами**. Числа скорости/качества из отчёта товарища не считаем независимо воспроизведёнными. Просмотрены статья, harness и исходный Map.cpp; тяжёлые окружения не добавлялись.

## Что реально запущено

### 1. Полная запись: только геометрия

Новый `tunnel_guard.rail_geometry_audit` заново читает реальные измерения, проверяет совпадение номера кадра и времени с сохранённым baseline, выполняет range/voxel preparation и TrackGeometry. Сравнивает доступность и расхождение путей, **не** точность рельсов. Deskew для этого replay запрещён, конфигурация берётся из baseline с одним явным изменением политики.

| Показатель | Baseline | Fitted initial heading |
|---|---:|---:|
| Кадры | 11271 | 11271 |
| Геометрия доступна | 11250 | 11258 |
| Геометрия недоступна | 21 | 13 |

Восстановлены кадры 898, 907, 6750, 8396, 8447, 8449, 8543, 8544, 10587. Новый отказ: **4094**. Ни одной принятой опоры вне продольных диапазонов обеих сторон. Это необходимое условие, но не доказательство, что выбрана правильная пара рельсов.

На общих доступных дистанциях 10/20/40/60 м максимальное по кадру изменение центра: медиана 0.000239 м, p95 0.1993 м, максимум **5.7151 м**. Это расхождение двух оценок, не ошибка относительно истины.

Причина отказа от автоматического продвижения: первый heading влияет на последующую последовательность выбранных пар. В кадре 8698 новая последовательность переходит с центра y=1.181 на x=30 к y=0.207 на x=36.47, после чего дальняя экстраполяция сильно меняется. В 8358 и 9083 аналогичный подозрительный скачок есть, наоборот, у baseline. В 4094 новая версия оставляет только первую опору. Проблема шире одного начального угла: критерий продолжения проверяется в центре поискового окна, а опора затем переносится к измеренному продольному диапазону без повторной проверки согласованности с предыдущей опорой. Необходима отдельная проверка непрерывности и конкурирующих пар; данные пока не доказывают правильность одной версии во всех этих случаях.

### 2. Полный детектор: фиксированная панель

798 кадров трёх исходных записей и 153 кадра трёх фиксированных сегментов extended. До изменения использовались `build/rail-measured-real` и `build/extended-measured`; конфигурации идентичны сохранённой конфигурации нового прогона. Отличался код направления.

| Показатель | До | Эксперимент |
|---|---:|---:|
| Реальные кадры | 951 | 951 |
| Доступная геометрия | 950 | 950 |
| Наблюдения подтверждённого пересечения | 524 | 523 |
| Наблюдения кандидатов ≥60 м | 54116 | 54122 |
| Истории с будущими / дублированными timestamps | 0 / 0 | 0 / 0 |

Нет пропусков, добавленных кадров или несовпадений идентичности измерений. Числа кандидатов не доказывают сохранение каждого объекта или рост recall. Неполная разметка не позволяет считать precision. Пять provisional-боксов совпали 5/5 при IoU≥0.25, среднее IoU=0.283728; это пять кадров одной геометрической структуры, не пять независимо подтверждённых препятствий. Конкурирующие запуски не являются измерением ускорения.

После введения явного экспериментального переключателя отдельно повторены **51 кадр в каждом режиме**. Все сравниваемые семантические поля (геометрия, объекты, статусы, позы, качество, расстояние) совпали с соответствующим сохранённым прогоном. Основной режим сохранил baseline.

### 3. Синтетические сценарии

7 случаев × 12 кадров × 2 версии = **168 обработанных облаков**. Хеши входных последовательностей попарно совпадают. В baseline загружался замороженный пакет из `build/extended-full/source`, а не текущий Detector. Порог совпадения с оболочкой видимых отражений — IoU≥0.1; это диагностический выбор, не критерий полевого приёмочного испытания.

| Сцена | Подтверждённое пересечение с объектом: до / после |
|---|---|
| Пустая, сенсор стоит / движется | 0 тревожных кадров / 0, в обоих вариантах |
| Неподвижный объект, старт 20 м | 11/12 / 11/12 |
| Неподвижный объект, старт 60 м | 11/12 / 11/12 |
| Неподвижный объект, старт 100 м | 0/12 / 0/12 |
| Движется, затем стоит | 12/12 / 12/12; после остановки 6/6 |
| Появляется в кадре 4 | кадры 5,6,8,9,10,11 в обеих версиях |

На 100 м **кандидат присутствует во всех кадрах**, best candidate IoU=1, по 3–4 отражения. Но последняя измеренная опора пути около 65 м; отношение к габариту `unresolved`, причина `unsupported_nominal_envelope`. Система не выдаёт доказанное пересечение без поддержки пути. На появляющемся объекте кадр 7 не проходит критерий совпадения подтверждённого бокса — провал сохранён.

Сцены идеализированы: прямой тоннель, упрощённые шум/пропуски, без реалистичных материалов, multipath и rolling acquisition. Эти результаты не устанавливают дальность обнаружения Pandar128 и не заменяют реальные препятствия.

## Команды и артефакты

Все команды выполнены через `.venv-iteration/bin/python`. Каталоги результатов не перезаписываются: для повтора задайте новый `output` в копии JSON. Исходные bags и baseline-артефакты необходимы для сравнения.

```bash
python -m tunnel_guard.rail_geometry_audit --experiment configs/rail-heading-prefix-geometry.json
python -m tunnel_guard.rail_geometry_audit --experiment configs/rail-heading-full-geometry.json
python -m tunnel_guard.run --experiment configs/rail-heading-real.json
python -m tunnel_guard.panel_report --panel configs/rail-heading-comparison.json --output build/rail-heading-real/comparison.json
python -m tunnel_guard.evaluate --run build/rail-heading-real --annotations annotations/sourcecraft-provisional.json --output build/rail-heading-real/evaluation.json
python -m tunnel_guard.motion_scenarios --experiment configs/motion-scenarios-heading.json
python -m tunnel_guard.run --experiment configs/rail-heading-final-replay.json
python -m tunnel_guard.run --experiment configs/rail-heading-default-replay.json
```

Baseline сценариев запускался так (новый runner, замороженные Detector/geometry/stress):

```bash
python -c 'import sys; from pathlib import Path; root=Path.cwd(); sys.path.insert(0,str(root/"build/extended-full/source")); import tunnel_guard; tunnel_guard.__path__.append(str(root/"tunnel_guard")); from tunnel_guard.motion_scenarios import main; main()' --experiment configs/motion-scenarios-before.json
```

Первоначальные полные прогоны выполнены до введения переключателя, когда экспериментальное направление было безусловным. Их source/config snapshots сохранены без изменений; текущие recipes явно включают эквивалентный режим. Повтор после переключателя — 51 кадр на режим, не повтор всей записи. Машиночитаемые результаты и хеши: `results/gerasimov-review-20260918.json`. Детальные облачные результаты, логи и исходники — `build/rail-heading-*`, `build/motion-scenarios-*`. Автоматизированные тесты не создавались и не запускались.

## Следующий приоритет

1. Исправить геометрическую согласованность после переноса опоры и проверить конкурирующие пары на всей реальной записи, сохранив также отказанные результаты. Не подгонять правило под перечисленные номера кадров.
2. Расширить процедуры до кривых/неоднозначных пар и вставок с корректным лучевым закрытием в реальные пустые тоннели. Отдельно оценивать сохранение кандидата и подтверждение пересечения с путём.
3. Использовать moving/static segmentation только как дополнительный признак, если независимое сравнение покажет пользу. Пока нет основания добавлять ML или большой runtime ради MOS.
