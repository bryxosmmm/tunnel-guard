# Следующая итерация: задачи команды

Общая база: ветка `experiments/morev`, включающая исходную разметку из `3e2d017`.
Цель: корректно измерять обнаружение, локализацию и ложные тревоги на реальных данных.
Сначала назначьте по одному владельцу на задачи A–C. Задача D остаётся у Morev.
Не нужно ждать завершения D, чтобы начать A–C.

## Как начать

Сохраните свою текущую работу, затем:

```sh
git fetch origin
git switch -c experiments/your-task origin/experiments/morev
```

Работайте в отдельной ветке. Отправляйте PR в `experiments/morev` на время этой
итерации; после общей проверки результат можно объединить с `main`.
Не меняйте пороги или разметку в чужой задаче. Данные bag и каталоги build не входят в Git.
Для каждой задачи: исходный commit, конфиг, точная команда, реальный вывод и ограничения.
Автотесты в проекте не создаём и не запускаем; проверяем реальными CLI/проездами.

## A. Разметка: отрицательные эпизоды и правила боксов

**Кому:** тиммейту, который размечал человека. **Ветка:** `experiments/reviewed-panel`.

Вход: `annotations/sustech-raw/doubleT_obstacle/`, реальные записи, существующий редактор.

1. Явно зафиксировать: полный предполагаемый объём объекта или границы видимых отражений.
   Сохранить происхождение: ручной якорь 181, перенос центров по треку, ручная проверка
   положения 165–200, постоянные размеры/поворот. Это не 36 независимых событий.
2. Выбрать и просмотреть 3–5 коротких эпизодов с разной инфраструктурой; по возможности
   включить прямую, платформу и кривую. Цель — найти проверяемые отрицательные интервалы,
   а не объявить запись пустой по её имени. Если видимость не позволяет — отметить unknown.
3. Для каждого: bag, диапазон кадров/времени, проверенная область/дальность, видимость,
   наличие объекта, пересечение пути (или unverified), автор и дата проверки.
   Флаг exhaustive ставить только для полностью проверенного выбранного scope. Текущий
   оценщик не умеет ограниченную пространственную область: не подменять ею exhaustive=true.
4. Сохранить исходные PSR, 3–5 иллюстраций и перечень неоднозначных случаев.

**Готово:** небольшой versioned JSON/manifest с реальными интервалами и протоколом
разметки. Не нужны тысячи боксов. Пустые/закрытые области не считаются свободными.

## B. Сенсор, время и наблюдаемость

**Кому:** второму тиммейту. **Ветка:** `experiments/sensor-profile`.

Вход: `docs/SENSOR_PROFILE.md`, `tunnel_guard/inspect_bag.py`, руководство Hesai и Q&A,
когда появится. Можно начать с документов и текущих bag без ожидания Q&A.

1. Составить таблицу «параметр / источник / измерено в bag / неизвестно»:
   точная модель, частота, return mode, оси, установка, timestamp, сборка скана,
   обработка драйвером, угловая/временная калибровка, фильтры сенсора.
2. На реальных кадрах проверить распределения времён, интервалы кадров и отражения
   по ring/дальности. Отличать размер массива, валидные точки и уникальные измерения.
3. Сформулировать короткие вопросы организаторам. Отправку согласовать с командой.

**Готово:** отчёт со ссылками на страницы руководства/таймкоды Q&A, командами и
артефактами. Отдельный вывод: что известно и чего не хватает для включения deskew.
Не включать deskew и verified-флаги только потому, что найдено руководство семейства.

## C. Ubuntu/Humble: запуск и измерение скорости

**Кому:** тиммейту с Ubuntu или доступом к Linux. **Ветка:** `experiments/humble-run`.

1. Воспроизвести офлайн CLI на том же `doubleT_obstacle` с кадра 0, сохранить журнал,
   versions, конфиг, CPU/RAM, p50/p95 и длительность записи/обработки.
2. Открыть RViz с `rviz/tunnel_guard.rviz` и проиграть result bag с одним `/clock`.
   Проверить облако, коридор, кандидатов, расстояние, качество; паузу и повторный запуск.
3. Записать точные шаги установки/запуска и короткое видео или скриншоты реального replay.
4. Профилировать обработку, назвать 2–3 самые дорогие стадии. Оптимизацию пока не смешивать
   с изменением качества; сначала получить профиль.

**Готово:** другой человек может повторить запуск. В отчёте явно отделены офлайн pipeline,
replay готовых результатов и live inference (последний этим заданием не подтверждается).
Не тратить время на аренду GPU: она для этой задачи не обязательна.

## D. Наша задача: корректная оценка и причины тревог

**Владелец:** Morev. **Ветка следующей реализации:** `experiments/oriented-evaluation`.

1. Сохранить PSR и описание ручной проверки; воспроизвести AABB/OBB сравнение на 36
   реальных наблюдениях без изменения размеров, IoU-порога и детектора.
2. Отдельно показывать обнаружение/сопровождение, пересечение пути, геометрию бокса и
   расстояние до наблюдаемой поверхности. Сначала определить правила соответствия;
   не засчитывать объект по одному произвольному близкому центру.
3. Разобрать расхождение центра (~0.48 м по сообщению автора): видимая поверхность против
   полного объёма, ошибка переноса или ошибка сегментации. Сохранить исходные метки.
4. После A разобрать постоянные тревоги. Выбрать один воспроизведённый источник ошибки,
   изменить его и сравнить на зафиксированных эпизодах. Промахи и неудачные варианты сохранять.

**Готово:** повторяемый отчёт с корректной семантикой метрик и одной доказанной следующей
задачей для детектора. Синтетические результаты не заменяют реальные отрицательные эпизоды.

## Дополнительный ресерч, если есть свободный человек

**Вопрос:** какие методы ground segmentation сохраняют низкие и редкие препятствия?
Начать с официальной реализации Patchwork++ и текущего `TrackGeometry`.
Результат первого этапа — краткая записка: требуемые входы, предпосылки, лицензия,
выход метода, режим отказа, стоимость интеграции и конкретный сравнительный эксперимент.
Следующий этап — запуск официальной реализации на фиксированных реальных кадрах с
анализом сохранённых точек объекта и времени. Не удалять все точки ground без оценки.
Сравнивать с текущим методом, а не объявлять новую реализацию лучше по картинке.

ML и карту пока не назначаем как обязательную задачу: сначала выясняем, какую измеренную
ошибку они должны исправлять. На этой итерации не меняем архитектуру целиком.
